# 國際化（i18n）規格

## 概述

Singular Blockly 支援 15 個 locale：`en`、`zh-hant`、`ja`、`ko`、`de`、`fr`、`es`、`it`、`pt-br`、`ru`、`pl`、`cs`、`hu`、`bg`、`tr`。

i18n 品質分成兩個互補層級：

- Deterministic validator 驗證可以客觀判定的結構、key、placeholder、編碼與 package NLS 契約。
- 工作區 `i18n-maintenance` Skill 依版本化政策審計語意、兒少可理解性、語氣、在地用詞、可及性與 UI 情境。

程式實際行為與核准規格是語意權威；英文 locale 是一般訊息的 key 與 placeholder 結構基準。CyberBrick 範例仍使用目標語系 → 英文 → 原始繁中的後援順序。

## 翻譯資料面

| Surface | 位置 | 基準與要求 |
| --- | --- | --- |
| WebView／Extension 訊息 | `media/locales/{locale}/messages.js` | 15 語系 key 必須完全一致 |
| VS Code manifest 文字 | `package.nls*.json` | 15 語系 key 必須完全一致 |
| 範例索引 | `media/samples/index.json` | title／description 支援 15 語系與英文 fallback |
| 範例識別字 | sample JSON `nameTranslations` | `en` fallback；已提供值須符合 ASCII identifier |
| 範例顯示字串 | sample JSON `stringTranslations` | `en` fallback；已提供值須為非空字串 |

Locale 訊息格式：

```javascript
window.languageManager.loadMessages('zh-hant', {
	NEW_FEATURE_LABEL: '新功能',
	PIN_TOOLTIP: '將腳位 {0} 設定為 {1}',
});
```

## Deterministic validation

### 指令

```bash
npm run validate:i18n
npm run validate:i18n:lang -- --language=ja
node scripts/i18n/validate-translations.js --all --format=json
npm run test:i18n
```

Validator 檢查：

- 15 個 locale 與 `package.nls` 的雙向 key 一致性，包含缺少與多餘 key。
- UTF-8、BOM、可解析結構、純字串值與空值例外。
- `{0}`、`%1`、`${name}` 等 placeholder 的名稱及出現次數。
- 必要 ARIA 訊息與對應 Blockly core locale 是否存在。

Exit code：`0` 通過、`1` 發現驗證錯誤、`2` 無法執行或設定錯誤。`--format=json` 的 finding 以 `code|surface|locale|key` 形成可重複的錯誤簽章。

字元長度比例不是語意或版面正確性的證明，因此不再產生 50%／150% 大量警告。可能溢出的 UI 應在實際元件與主題中驗證。

## 語意政策與 gate

工作區 Skill 的版本化政策位於 `.github/skills/i18n-maintenance/references/`。每個 finding 必須同時記錄規則 ID、severity、evidence、來源、目標與具體情境。

| Severity | 定義 | Gate |
| --- | --- | --- |
| Blocker | 意義反轉、安全／操作錯誤、技術事實破壞 | 已證實項目必須為 0 |
| Major | 明顯歧義、兒少難以理解、違反核准術語或 locale 政策 | 本次明確違規必須修復 |
| Minor | 不影響意思的自然度、地域偏好或 UI 建議 | 不阻擋 |
| Info | 未來可考慮的現代化或一致性整理 | 不阻擋 |

Evidence 使用 `deterministic`、`policy-backed`、`context-backed`、`ambiguous`，不得以模型自評百分比替代。`ambiguous` Major 必須提供回譯與候選方案，由產品負責人明確選擇或註記風險。

## 增量修復與完整審計

翻譯變更、Git 流程與發布 review 會觸發 `i18n-maintenance`：

1. 先以 JSON validator 找出客觀錯誤。
2. 只修正本次 diff；英文新增 key 時，對應 14 個目標 locale 都算本次範圍。
3. 每輪重新執行硬檢查與語意複審，最多三輪；問題未下降、同一簽章連續兩輪或譯文震盪時停止。
4. 以 `PASS`、`PASS_WITH_ADVISORIES`、`NEEDS_USER_DECISION` 或 `BLOCKED` 結案。

`docs/specifications/02-internationalization/audit-state.json` 保存政策版本、上次完整審計時間、manifest、checkpoint 與未結案 Blocker／Major。狀態缺失、已滿 30 天、政策版本改變或明確要求 `audit-all` 時，使用下列 helper 將全語料固定分成每批 200 組：

```bash
node scripts/i18n/prepare-semantic-audit.js
node scripts/i18n/prepare-semantic-audit.js --batch=1
```

批次審計不自動改寫既有翻譯。中斷後依 checkpoint 續跑；manifest 改變時重新開始。全量既有 Blocker 阻擋發布，既有 Major 只形成待辦，不擴張目前 PR。

Helper 會驗證 audit state 的 schema version、必要欄位、四級非負 counts、完成時間及 cursor 範圍。`state-schema-changed`、`invalid-state` 或 manifest 改變都不得沿用舊 checkpoint，必須依目前語料從 batch 1 安全重建。

## 新增或修改文字

1. 先確認 call site 的實際操作、後果與訊息類型。
2. 在英文基準新增或修改 key，並同步全部 14 個目標 locale。
3. 保留 placeholder、技術名稱、數值、單位與可逆性。
4. 依 `i18n-maintenance` 的 semantic policy 與相關 locale profile 審計。
5. 執行 `npm run validate:i18n`、`npm run test:i18n` 與受影響的 UI／contract tests。
6. 使用 localization PR template 記錄 finding ID、重要前後對照、waiver 與 UI 驗證。

面向 8–14 歲的警告需讓使用者理解「發生什麼、要做什麼、結果是什麼」，但必要的 Node.js、Blockly、CyberBrick 等技術名稱應保留並在情境中說明。更具體的安全警告與範例名稱契約見 [user-facing-localization.md](user-facing-localization.md)。
