# 功能規格：Singular Core 的 Windows 短路徑工作區

**功能分支**：`claude/project-thread-cwsbzq`（雲端工作階段指定分支）

**建立日期**：2026-11-26

**狀態**：Draft

**輸入**：Ray 要求分析並修正「Singular Core 遇到長路徑」的問題（2026-11-26）。分析結果：067 的 issue #130／#132 修正只保護了 Core 本身安裝階段（Python 與 pip scratch）的 Windows 260 字元路徑預算；Arduino ESP32 工作流退回 Singular Core 時，PlatformIO 會把平台套件、工具鏈與編譯輸出放在預設 global storage 之下，以最短的使用者名稱推算，最深的套件檔案仍約 299 字元，在未啟用 Windows long paths 的電腦上會失敗，而且失敗目前不會被辨識成路徑過長。

## Clarifications

### Session 2026-11-26

依 `sdd-gate.md`「clarify 有合理預設時寫進 Assumptions 繼續」，以下問題以預設答案處理，沒有另外詢問 Ray：

- Q：使用者自訂 managed runtime 資料夾但太深時，要不要自動改用其他候選？→ A：不要。尊重使用者明確的選擇，只回報路徑過長並引導換資料夾（FR-003）。
- Q：要不要順便把 Core 本身搬到短位置？→ A：不要。Core 的安裝路徑已有 067 的預算檢查保護；搬移會迫使所有既有使用者重新下載（FR-009，超出範圍）。
- Q：`system-drive` 候選是否在 ASCII 的使用者資料夾也會被使用？→ A：會，但只在 `local-app-data` 超出預算時（例如很長的網域帳號資料夾），順序固定為 FR-003。
- Q：Windows CI 要不要完整編譯 ESP32 專案？→ A：至少安裝 ESP32 平台與工具鏈並記錄最長路徑；完整編譯納入同一個工作，時間預算允許時一併執行（FR-013）。

## 使用者情境與測試 *(必填)*

### 使用者故事 1－Windows 上用 Singular Core 編譯 ESP32（優先級：P1）

學生在 Windows 電腦上使用預設設定，沒有啟用 long paths，也沒有可用的 PlatformIO／PIOArduino provider（例如 provider 損壞，或在沒有 provider 的編輯器中）。學生編譯並上傳 ESP32 專案時，Singular Core 能下載平台與工具鏈並完成編譯，不需要學生改登錄檔、改設定或請管理員協助。

**優先此項的理由**：Arduino 工作流把 Singular Core 當作 provider 的備援。備援在 Windows 上一碰到 ESP32 就失敗，等於備援承諾在最常見的教室電腦設定下不成立。

**獨立測試方式**：在 `LongPathsEnabled=0` 的乾淨 Windows x64 上，只使用 Singular Core 安裝 ESP32 平台與工具鏈並編譯範例專案；另以決定性測試驗證各種使用者資料夾長度下選出的工作位置都符合路徑預算。

**驗收情境**：

1. **給定** Windows 未啟用 long paths、使用者資料夾名稱只有 ASCII、managed runtime 使用預設位置，**當** 學生第一次用 Singular Core 編譯 ESP32 專案，**則** 平台、工具鏈與編譯輸出都放在符合 260 字元預算的短工作位置，並且編譯成功。
2. **給定** Windows 使用者資料夾包含中文等非 ASCII 字元，**當** 學生用 Singular Core 編譯 ESP32 專案，**則** 系統改用只含 ASCII 的短工作位置，不讓工具鏈收到非 ASCII 路徑。
3. **給定** 學生在 macOS 或 Linux 上，**當** 學生用 Singular Core 編譯，**則** 行為與現在相同，不建立新的工作位置。

### 使用者故事 2－放不下時提早而清楚地失敗（優先級：P1）

如果在這台電腦上找不到放得下 ESP32 套件的位置（例如使用者自訂了很深的 managed runtime 資料夾），學生在花時間下載前就看到「需要較短的資料夾」的說明，並能一鍵打開對應設定。如果編譯途中仍因路徑太長失敗，也看到同一個說明，而不是一般的失敗訊息。

**優先此項的理由**：下載 ESP32 工具鏈要好幾分鐘。下載完才失敗、而且訊息看不出原因，會讓老師與學生無從排除。

**獨立測試方式**：以決定性測試模擬過深的自訂資料夾與 PlatformIO 回傳的長路徑錯誤輸出，確認兩者都歸類為路徑過長，並顯示既有的「選擇較短資料夾」動作。

**驗收情境**：

1. **給定** 所有候選工作位置都超過路徑預算，**當** 學生用 Singular Core 編譯或安裝套件，**則** 系統在啟動 PlatformIO 前就停止，顯示路徑過長說明與「選擇較短資料夾」動作，且不修改 provider。
2. **給定** PlatformIO 或工具鏈在編譯、安裝套件時輸出路徑過長或找不到深層檔案的錯誤，**當** 系統分類這次失敗，**則** 結果是路徑過長，而不是一般失敗。

---

### 使用者故事 3－既有使用者不必重裝（優先級：P2）

已經準備好 Singular Core 的使用者（多數是 CyberBrick 使用者）更新到新版後，不需要重新下載 Python 與 PlatformIO Core。Core 本身維持原位置；只有之後才會下載的 PlatformIO 平台、套件與編譯輸出改放到短工作位置。

**優先此項的理由**：重新下載 Core 要花時間與流量，對學校網路是明顯負擔；而受影響的只有尚未成功下載過的 ESP32 套件。

**獨立測試方式**：以既有版本的 managed runtime 狀態啟動新版，確認 current record、Python 與 mpremote 原地重用，CyberBrick 上傳流程不變。

**驗收情境**：

1. **給定** 舊版已準備好的 Singular Core，**當** 使用者更新並重新啟動 VS Code，**則** 不重新下載 Core，CyberBrick 上傳與裝置偵測照常運作。
2. **給定** 舊版在 Core 底下留下的平台套件或編譯輸出，**當** 使用者執行既有的「清理受管檔案」，**則** 這些已不再使用的舊檔案可以被清掉，且不碰目前使用中的 Core、provider、專案或未知檔案。

---

### 使用者故事 4－短工作位置只屬於這位使用者（優先級：P1）

學校電腦常有多個 Windows 帳號共用。短工作位置裡的工具鏈會被執行，因此其他帳號不能預先建立、替換或修改其中的檔案。

**優先此項的理由**：磁碟根目錄底下新建的資料夾預設會讓所有已登入使用者修改子檔案；若直接沿用，其他帳號可以替換工具鏈，在學生的帳號下執行任意程式。

**獨立測試方式**：以決定性測試驗證系統只採用自己建立並帶有本機擁有權標記的位置；在 Windows CI 檢查新建位置的存取權只授予目前使用者、SYSTEM 與 Administrators。

**驗收情境**：

1. **給定** 候選位置已存在但不是由本使用者的 Singular Blockly 建立，**當** 系統選擇工作位置，**則** 不採用它，改試下一個候選，最後才顯示路徑過長說明。
2. **給定** 系統在共用位置（例如磁碟根目錄）建立工作位置，**當** 建立完成，**則** 該位置移除繼承的寬鬆權限，只保留目前使用者、SYSTEM 與 Administrators。
3. **給定** 無法設定這些權限，**當** 系統選擇工作位置，**則** 不使用該候選，並刪除剛建立的空資料夾。

---

### 使用者故事 5－看得到、測得到（優先級：P3）

維護者與進階使用者可以在 PlatformIO 診斷面板看到短工作位置（以隱私化標記顯示）、目前選用的是哪一類候選，以及 Windows long paths 是否已啟用。合併前的 Windows CI 會實際安裝 ESP32 平台套件，防止之後的改動再次讓路徑超長。

**優先此項的理由**：這個問題在 Ray 的實機測試與既有 CI 中都沒被抓到，原因是兩者都沒有在 Windows 上透過 Singular Core 安裝 ESP32 套件。

**獨立測試方式**：檢查診斷輸出與 AI repair packet 不含完整路徑；在 Windows CI 跑 ESP32 套件安裝並收集最長路徑的證據。

**驗收情境**：

1. **給定** 使用者開啟 PlatformIO 診斷，**當** 面板顯示 Singular Core 卡片，**則** 顯示短工作位置的隱私化標記、候選類別與 long paths 狀態，不顯示完整路徑。
2. **給定** 有人修改 managed runtime 或 PlatformIO 環境設定，**當** Windows CI 執行，**則** 透過 Singular Core 安裝 ESP32 平台套件成功，並記錄最長的實際路徑長度。

### 邊界情境

- 使用者已設定 `singularBlockly.managedRuntime.path`：工作位置放在該資料夾內，不自動改到其他位置；超出預算時顯示路徑過長說明。
- 使用者資料夾名稱很長（Windows 帳號名稱最多 20 字元，但網域帳號的資料夾可能帶有 `.DOMAIN` 後綴）：依序嘗試較短的候選。
- 磁碟根目錄不允許一般使用者建立資料夾（鎖定的學校映像）：跳過該候選。
- 兩個 VS Code 視窗同時第一次選擇工作位置：只有一個建立成功，另一個採用同一個已驗證的位置，不重複建立。
- 工作位置被使用者或防毒軟體刪除：下次使用時重新選擇並建立，只重新下載 PlatformIO 套件，不重裝 Core。
- 使用中的工作位置之後被其他帳號竄改權限：下次使用前驗證擁有權標記，不符就不使用。
- Provider Core：完全不受影響，不讀寫其 `.platformio` 資料夾。

## 需求 *(必填)*

### 功能需求

- **FR-001**：在 Windows 上，Singular Core 執行 PlatformIO 時，平台、套件、套件快取、專案編譯輸出與專案函式庫必須放在「短工作位置」，不放在 managed runtime 的版本資料夾底下。
- **FR-002**：短工作位置必須依固定順序從候選中選出第一個同時符合以下條件的位置：只含 ASCII 字元、位於本機磁碟、預計的最深套件路徑與最深編譯路徑都低於 260 字元、由本使用者的 Singular Blockly 建立或可以由它安全建立。
- **FR-003**：候選順序為：(1) 使用者自訂 managed runtime 資料夾時，只用該資料夾內的固定子資料夾；(2) 否則先用本使用者的本機應用程式資料夾（非漫遊）；(3) 再用系統磁碟根目錄下、以本使用者識別雜湊區分的資料夾。全部不符合時以 `path-too-long` 停止。
- **FR-004**：路徑預算必須分別保留 ESP32 平台套件與工具鏈所需的後代路徑長度，以及專案編譯輸出與函式庫的後代路徑長度。保留值以實際量測的最深檔案為基準，並保留餘裕。
- **FR-005**：專案編譯輸出與函式庫的資料夾名稱必須使用固定長度的短識別碼，以專案 URI 雜湊產生，不可使用完整 64 字元雜湊。
- **FR-006**：系統建立在共用位置的工作位置時，必須移除繼承權限，只授權目前使用者、SYSTEM 與 Administrators；無法完成時不使用該位置。
- **FR-007**：系統只能採用帶有有效擁有權標記、且標記與本使用者記錄一致的既有位置。不認得的既有資料夾一律不採用、不修改、不刪除。
- **FR-008**：PlatformIO 或工具鏈在安裝套件、編譯或上傳時輸出路徑過長的特徵，必須歸類為 `path-too-long`，顯示既有的路徑過長通知與「選擇較短資料夾」動作。
- **FR-009**：已準備好的 Singular Core（current record、Python、PlatformIO Core、mpremote）必須原地沿用，不因本功能重新下載。
- **FR-010**：既有的「清理受管檔案」必須能移除舊版放在 Core 版本資料夾底下的平台、套件與快取，以及短工作位置中已不再被任何專案使用的編譯輸出；不得觸碰目前使用中的 Core、provider、專案或未知檔案。
- **FR-011**：PlatformIO 診斷與 AI repair packet 必須以隱私化標記顯示短工作位置與候選類別，並顯示 Windows long paths 是否啟用；不得輸出完整路徑或使用者名稱。
- **FR-012**：macOS 與 Linux 的路徑與行為必須保持不變。
- **FR-013**：Windows CI 必須透過 Singular Core 實際安裝 ESP32 平台與工具鏈，並把最長實際路徑長度列入隱私化證據。
- **FR-014**：本功能不得要求或自動變更 Windows 登錄檔、群組原則、`subst` 磁碟代號或 junction，也不得要求系統管理員權限。

### 核心概念

- **短工作位置（PlatformIO work root）**：Singular Core 在 Windows 上放 PlatformIO 平台、套件、快取、編譯輸出與專案函式庫的本機資料夾。與 Core 版本資料夾分開，可安全刪除後重建。
- **候選類別**：`custom`（使用者自訂資料夾內）、`local-app-data`（使用者本機應用程式資料夾）、`system-drive`（系統磁碟根目錄下的個人資料夾）。
- **擁有權標記**：位於工作位置根目錄的檔案，記錄建立者、建立時間與隨機識別；該識別也存在 Extension 自己的儲存中，兩者一致才採用。
- **路徑預算**：工作位置長度加上量測過的後代保留長度，必須低於 260 字元。

## 成功指標 *(必填)*

### 可量測目標

- **SC-001**：在 `LongPathsEnabled=0` 的乾淨 Windows x64 上，ASCII 使用者名稱、預設設定下，只用 Singular Core 第一次編譯 ESP32 範例專案成功。
- **SC-002**：使用者名稱為 1 到 20 個字元（含非 ASCII 名稱與網域後綴）的情況下，選出的工作位置加上保留長度 100% 低於 260 字元；所有候選都不符合時，100% 在啟動 PlatformIO 前回報路徑過長。
- **SC-003**：從舊版更新的使用者，Core 重新下載次數為 0。
- **SC-004**：PlatformIO 已知的路徑過長錯誤輸出樣本 100% 歸類為路徑過長。
- **SC-005**：診斷輸出、剪貼簿內容與日誌中出現完整工作位置路徑或使用者名稱的次數為 0。
- **SC-006**：Windows CI 透過 Singular Core 安裝 ESP32 套件成功，且記錄的最長實際路徑低於 260 字元。
- **SC-007**：macOS 與 Linux 既有 managed runtime 測試全部維持通過，路徑不變。

## 假設

- 依 Ray 2026-11-26 的指示「開始修吧」，採用分析時推薦的方向：把 PlatformIO 的重型資料夾移到短路徑，而不是要求使用者開啟 long paths。
- 非 ASCII 使用者資料夾的備援位置採用系統磁碟根目錄，這與 PlatformIO IDE 本身的做法一致：Windows 上使用者資料夾含非 ASCII 字元時，PlatformIO IDE 會改用 `<磁碟>:\.platformio`（`platformio-node-helpers` 11.3.0 的 `getCoreDir`）。為避免磁碟根目錄繼承的寬鬆權限，本功能另外收緊存取權（FR-006）。
- ESP32 是目前最深的套件。量測 `espressif32@7.0.1` 使用的 `framework-arduinoespressif32 3.20017` 與 `toolchain-xtensa-esp32 8.4.0+2021r2-patch5`（windows_amd64），套件資料夾以下最深的相對路徑分別是 144 與 142 字元（含套件資料夾名稱）。
- 本功能只處理 Singular Core。Provider Core 的 `.platformio` 位置由 provider 管理，本功能不變更。
- 硬體實測依「發布門檻」：合併前需要 Ray 在 Windows 實機上用 Singular Core 編譯並上傳一次 ESP32。

## 超出範圍

- 開啟或引導開啟 Windows `LongPathsEnabled`（只在診斷中顯示狀態）。
- 搬移已安裝的 Core 本身（Python、penv、PlatformIO Core）到新位置。
- 變更 provider 的 PlatformIO 位置或設定。
- 其他作業系統的路徑調整。
