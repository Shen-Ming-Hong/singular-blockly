# 功能規格：圖形化積木設計器

**Feature Branch**: `claude/project-thread-zeku61`\
**Created**: 2026-10-29\
**Status**: 已實作（實驗設定後，待 Ray 硬體實測）\
**Input**: Ray（2026-10-29）：「客製化流程錯了，應該是要透過圖形化的方式客製化積木外觀，然後會產生基本的 code 框架（func），剩下的核心功能再請使用者填入。」延續 `072-esp32-block-packs`：積木包仍只支援 ESP32 DevKit、仍在實驗設定 `singular-blockly.experimental.blockPacks` 後面；本功能把「先手寫積木包檔再匯入」改成「在編輯器裡畫積木、填函式本體」，匯入改為分享用途。

## Clarifications

### Session 2026-10-29

- Q：積木形狀怎麼選？ → A：用圖形點選，不用下拉選單；形狀必須符合業界標準，直接取自 Blockly thrasos 渲染器畫出的實際外形（Ray）。
- Q：分類顏色怎麼選？ → A：一個色塊，點開是完整 RGB 調色盤；積木包 `category.colour` 因此接受 `#rrggbb`，舊的 0–360 色相仍可用（Ray）。
- Q：函式本體要檢查什麼？ → A：基本回傳值檢查——缺 return、空 return、只做動作卻回傳值、回傳型別明顯不符（文字積木回傳數字常值或真假、數字／真假積木回傳字串）；有問題不能儲存。真正能否編譯由 PlatformIO 建置判斷（Ray）。
- Q：函式庫怎麼加？ → A：提供說明，並可直接搜尋 PlatformIO Registry、一鍵加入 `libDeps` 與標頭檔（Ray）。
- Q：設計畫布的滑鼠滾輪？ → A：縮放，不是捲動（Ray）。
- Q：接積木的插槽要不要預設值？ → A：要；依型別給數字、真／假或文字預設值，工具箱積木帶著對應的預設積木（Ray）。
- Q：積木清單裡輸入欄位怎麼表示？ → A：顯示參數名稱的小標籤，不用看不懂的方框（Ray）。
- Q：核心程式寫在哪？ → A：暫定在設計器的程式框（決策卡建議選項，Ray 尚未選擇；若改為產生 .h 檔，FR-003、FR-004、FR-005、FR-007 需修訂）。
- Q：手寫積木包在設計器怎麼顯示？ → A：不提供編輯按鈕，只能整包更新或移除（取代原本的唯讀顯示）。
- Q：函式名稱怎麼決定？ → A：由使用者在積木上填寫，設計器檢查 C++ 識別字、關鍵字與跨分類重名，不自動加前綴。
- Q：刪除輸入後，舊實例接在那個輸入上的積木？ → A：移到工作區頂層，不刪除，載入不會失敗；整個積木被刪除時沿用 072 的確認與佔位積木。
- Q：設計器加入的函式庫要不要匯入時的信任確認？ → A：函式庫是作者自己加的，儲存時不再跳確認；匯出後別人匯入時仍走 072 的信任與確認。

## 使用情境與驗收

### 使用情境一：畫出一個新積木並馬上使用（P1）

老師在 ESP32 DevKit 專案打開積木設計器，替新的感測器做一個「讀取距離」積木：輸入積木上的文字、加入兩個腳位欄位、選擇「回傳數字」形狀並挑顏色。設計器一邊編輯一邊顯示積木實際外觀，並自動寫好函式開頭與結尾，老師只在函式本體裡填入量測程式。儲存後，工具箱出現這個積木的分類，學生拖進主程式即可產生可編譯的程式碼。

**獨立驗收**：不寫任何 JSON，只用設計器做出一個含兩個腳位、回傳數字的積木，填入函式本體並儲存；放進主程式後產生的程式碼包含該函式與正確的呼叫，可在 ESP32 DevKit 編譯。

1. **假設** 專案板子為 ESP32 DevKit 且實驗設定已開啟，**當** 使用者開啟積木設計器並新增積木，**則**看到一個可編輯的積木與即時預覽。
2. **假設** 使用者在積木上加入文字片段與輸入欄位（腳位、數字、文字、下拉選單、接其他積木的值輸入），**當** 調整順序或刪除欄位，**則**預覽中的積木外觀立即同步。
3. **假設** 使用者選擇積木形狀（執行一件事、回傳數字、回傳真假、回傳文字），**當** 形狀或輸入改變，**則**函式框架的回傳型別與參數列表自動更新，參數名稱、型別與輸入一一對應。
4. **假設** 使用者在函式本體填入程式並儲存，**當** 回到編輯器，**則**工具箱出現該分類與積木，可直接拖用，不需重新開啟編輯器。
5. **假設** 積木放在主程式中，**當** 產生程式碼，**則**輸出一次函式定義，並在積木位置輸出以各輸入值為引數的函式呼叫。

### 使用情境二：修改積木時不會弄丟已寫好的程式（P1）

老師已經寫好函式本體，之後想多加一個「量測次數」數字欄位，或把欄位改名。

1. **假設** 函式本體已有內容，**當** 新增、刪除、改名或重新排序輸入，**則**只有函式開頭（回傳型別、函式名稱、參數列）重新產生，本體文字原封不動。
2. **假設** 本體引用了一個已被刪除的參數，**當** 使用者儲存，**則**設計器提醒該參數已不存在，仍允許儲存（程式正確性由作者負責）。
3. **假設** 工作區已有用到這個積木的實例，**當** 新增欄位後儲存，**則**既有實例保留原有欄位值，新欄位使用預設值；刪除的欄位值被丟棄，原本接在被刪除插槽上的積木移到工作區頂層；刪除整個積木時先提示受影響的積木數量。

### 使用情境三：分享設計好的積木（P2）

老師把做好的積木分類匯出成積木包檔，交給其他老師或學生匯入；匯入者也可以打開設計器繼續修改。

1. **假設** 專案中有用設計器做的積木分類，**當** 使用者選擇匯出，**則**產生一個積木包檔，內容可被 072 既有的匯入流程接受。
2. **假設** 他人匯入這個檔案，**當** 開啟設計器，**則**看到相同的積木外觀與函式本體，可再修改。
3. **假設** 匯入的是 072 格式、沒有設計資訊的手寫積木包，**當** 使用者在積木包清單中查看，**則**不提供編輯按鈕，只能整包更新或移除。

### 使用情境四：需要函式庫或初始化的積木（P2）

老師要包裝需要 Arduino 函式庫的模組（例如 DHT11）。

1. **假設** 使用者在設計器的進階區加入標頭檔、PlatformIO 函式庫（`owner/name@version`）、全域宣告與初始化程式，**當** 儲存，**則**這些內容每份程式只輸出一次，函式庫依賴沿用 072 的信任與確認規則。
2. **假設** 函式庫名稱不是 `owner/name@version` 格式或是網址，**當** 儲存，**則**拒絕並指出欄位。

### 使用情境五：內層語句積木（P3）

老師要做一個「如果溫度高於 30 度就執行」的積木。

1. **假設** 使用者在積木中加入「內層語句」欄位，**當** 設計器產生框架，**則**函式回傳真假，積木的程式碼是「如果函式回傳真，就執行內層積木」；同一積木最多一個內層語句欄位。

### 邊界情況

- 只有 ESP32 DevKit 顯示設計器入口；實驗設定關閉時入口隱藏，與 072 一致。
- 積木名稱、分類 id 與輸入名稱由設計器依使用者輸入產生合法識別字，並避免與 C++ 關鍵字、內建積木、其他積木包衝突；使用者看到的是自己輸入的顯示文字。
- 函式名稱由使用者填寫；設計器拒絕非 C++ 識別字、C++ 關鍵字，以及與同分類或其他積木包相同的函式名稱。
- 參數型別依輸入推導：腳位與數字為整數或小數（依數字欄位是否有小數位）、文字為字串、下拉選單依選項值、值輸入依設定的資料型別、真假為布林。
- 一個積木至少要有一段文字；不能有兩個同名輸入；下拉選單至少一個選項。
- 函式本體不在編輯器中執行，只做文字保存與插入；本體空白也可以儲存，產生的程式會以回傳型別的預設值收尾，確保可編譯。
- 設計器開著時切換板子或關閉編輯器，未儲存的變更需詢問是否放棄。
- 刪除整個分類沿用 072 的移除確認與佔位積木機制。

## 需求

### 功能需求

- **FR-001**：在 ESP32 DevKit 且實驗設定開啟時，使用者可從積木包視窗開啟積木設計器，新增分類、在分類中新增、編輯、刪除積木。
- **FR-002**：設計器以圖形化方式編輯積木外觀：文字片段、輸入欄位（腳位、數字、文字、下拉選單、值輸入、內層語句）、欄位順序、積木形狀與分類顏色，並即時顯示與工具箱相同外觀的積木預覽。
- **FR-003**：設計器依形狀與輸入自動產生函式框架，包括回傳型別、函式名稱、參數列，以及積木在程式中的呼叫方式；使用者只能編輯函式本體與進階區內容，框架開頭與呼叫方式不可手改。
- **FR-004**：輸入變更時只重新產生框架開頭，保留使用者寫的函式本體；本體引用已不存在的參數時給予提醒。
- **FR-005**：設計結果存成專案內的積木包，沿用 072 的儲存位置、型別前綴、程式產生、驗證、佔位積木與孤立積木保護；設計資訊（含函式本體）一併保存，讓重新開啟設計器時能還原。
- **FR-006**：儲存後工具箱立即更新；工作區既有實例保留仍存在欄位的值，刪除欄位造成影響時先說明受影響數量。
- **FR-007**：使用者可把一個分類匯出成積木包檔；匯出檔可被 072 匯入流程接受，並保留設計資訊供對方繼續編輯。
- **FR-008**：沒有設計資訊的積木包不提供編輯入口，只能整包更新或移除。
- **FR-009**：進階區可設定標頭檔、函式庫依賴、全域宣告與初始化程式，規則沿用 072（函式庫格式、每份程式只輸出一次；匯入他人積木包時的工作區信任與使用者確認）；可搜尋 PlatformIO Registry 並一鍵加入函式庫與其標頭檔。
- **FR-010**：設計器的介面文字、提示與錯誤訊息支援 15 個語系；積木顯示文字以使用者輸入的語言保存。
- **FR-011**：專案 Skill 與文件說明設計器產生的積木包格式，AI 修改工作區時能正確使用這些積木。
- **FR-012**：功能維持在實驗設定後、預設關閉；外觀需 Ray 確認、硬體需 Ray 實測後才可預設開啟。

### 主要實體

- **積木設計（Block Design）**：一個積木的外觀定義（文字片段、輸入、形狀）加上使用者寫的函式本體。
- **分類設計**：一組積木設計、分類名稱與顏色、進階區內容；存成一個積木包。
- **函式框架**：由積木設計推導的函式開頭與呼叫方式，不由使用者直接編輯。

## 成功標準

- **SC-001**：第一次使用的老師，在 5 分鐘內不看文件做出一個含兩個輸入、回傳數字的積木並在主程式中使用。
- **SC-002**：用設計器做出的範例積木（涵蓋腳位、數字、下拉、值輸入、內層語句、函式庫依賴各至少一次）產生的程式在 ESP32 DevKit 100% 編譯通過。
- **SC-003**：在已有函式本體的積木上增刪改輸入 20 次，函式本體 0 次遺失或被改動。
- **SC-004**：匯出再匯入到另一個專案後，積木外觀、產生的程式碼與函式本體完全相同。
- **SC-005**：使用者完成整個流程不需要手動編輯任何 JSON 檔。

## 假設

- 函式本體在設計器內的程式碼框填寫，與積木一起存在專案（見 Clarifications 最後的決策狀態）。
- 第一版只支援 ESP32 DevKit 與 Arduino C++；MicroPython 板子不在範圍。
- 積木顯示文字第一版只保存一種語言（使用者當下的介面語言），不在設計器中編輯多語系翻譯。
- 程式碼框提供等寬字型與縮排及基本回傳值檢查，不提供語法上色或編譯檢查；編譯錯誤由 PlatformIO 建置回報。是否嵌入程式碼編輯器（例如 CodeMirror）視核心程式位置的決定再議。
- 072 的匯入流程保留，用途改為分享；手寫 JSON 積木包仍可匯入但不是主要流程。
